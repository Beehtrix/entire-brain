# Own a Workspace Slice

You own one coherent vertical slice. Read normal global and project instructions, the Linear issue, and the parent dispatch packet. Normal skill, plugin, extension, and project-instruction discovery must remain enabled.

The dispatch packet is the requirements contract:

1. desired outcome and why it matters;
2. Linear issue ID and authoritative issue requirements;
3. settled product decisions and hard constraints;
4. cross-piece interfaces and dependencies;
5. acceptance signals and granted authority;
6. known evidence, separate from hypotheses.

Parent-supplied repository files, symbols, architecture, and implementation steps are hypotheses unless marked as directly verified evidence. Validate or discard them through independent repository exploration; do not follow a false technical hint merely because it appeared in the packet.

## Own the full repository workflow

Continue without parent approval through:

1. deep exploration sufficient to understand the repository and replace bad hypotheses;
2. the appropriate spec and implementation plan;
3. test-first delegated implementation for behavior changes;
4. complete repository verification and full-diff inspection;
5. PR creation and review follow-up to merge readiness.

The workspace controller owns exploration, specification, planning, and coordination. After planning, it **MUST NOT directly implement application code after planning**. It may write only specs, ephemeral plans, coordination ledgers/receipts, and exact transcription of non-application configuration when existing global or project policy already allows that writing. This narrow allowance does not permit application-code implementation or broaden any existing policy.

For Claude workspaces, explicitly invoke the enabled Superpowers workflow appropriate to the work: `superpowers:brainstorming`, `superpowers:writing-plans`, `superpowers:test-driven-development`, `superpowers:subagent-driven-development`, receiving-review, and verification-before-completion. After planning, invoke `superpowers:subagent-driven-development` for application implementation and use fresh review agents for review; do not substitute direct controller edits. During deep exploration, use `using-agent-knowledge-base` when recurring behavior may have durable prior evidence, but validate note claims against current repository and authoritative sources. Before the final receipt, evaluate verified reusable discoveries with `capturing-agent-knowledge`; its vault-note ownership rules are separate from this workspace's checkout ownership.

For Pi workspaces, explicitly invoke the approved `brainstorming`, Pi-native `writing-plans`, Pi `pi-subagents` roles/workflow, `test-driven-development`, `receiving-code-review` as applicable, and `verification-before-completion` workflows. After planning, dispatch application implementation to a Pi-native `pi-subagents` writer and use fresh review roles/workflow; do not substitute direct controller edits. Keep implementation plans ephemeral and outside the tracked tree. If a required named Pi agent or workflow is unavailable, inspect the Pi registry and either report the missing agent/workflow or adapt it within the approved Pi-native workflow; do not silently substitute another harness or bypass the required workflow with direct implementation.

Direct/inline execution is forbidden unless the user explicitly requests it. That explicit exception permits only the requested direct execution; it does not waive planning, verification, or fresh review. Workflow launch or tooling failure is a blocker, not permission to implement directly: record the failure and escalate it rather than bypassing the workflow.

Follow project instructions where they are stricter. Do not mutate Linear state, create dependencies, or close the issue. Report scope discoveries to the parent instead.

## Own PR review follow-up

For PR-bound work, create the human-authored PR first, then confirm its automatically created or linked trail before review. If automatic linking is absent, report the integration problem; do not fall back to `entire trail create`. Start and own the review steward in this checkout.

The owner remains accountable for review-loop liveness, may inspect aggregate state, and may nudge or resume the steward. Once started, the steward is the sole writer in the checkout: it reads detailed CI, Bugbot, thread, and trail feedback; implements fixes, verifies, commits, pushes, and follows review feedback through merge readiness. The owner must not edit, commit, or push while the steward owns the checkout. Owner intervention requires an explicit steward stop or release and a recorded handoff before any write.

Trail monitor review is mandatory on every steward wave, not only when a user mentions Slopgate. Require the steward to fetch authenticated Trail detail and record the current PR and Trail heads plus each monitor present in `.monitors[]` with its key, value, state, and evaluated SHA. Only monitors present in `.monitors[]` are configured. An absent Confidence, Risk, Security, or Slop key is `not configured`, does not block readiness, and does not create `insufficient_evidence`. Interrogate a present current Slop evaluation at every value. Confidence, Risk, and Security require interrogation when a current value, trend, or rationale names a concrete concern. Every monitor claim must have one canonical classification (`actionable_bug`, `actionable_cleanup`, `already_fixed_or_stale`, `non_actionable_opinion`, or `insufficient_evidence`), an explicit disposition, and steward-held code/test/diff/spec evidence. `insufficient_evidence` blocks readiness; stale and opinion claims are documented `no-action`, never silently dropped. Resume the sole-writer steward with only verified claims and evidence; do not turn monitor rationale into a fix instruction yourself.

Reconcile `trail-review=missing` against authenticated Trail detail before nudging or retriggering. Select from `.runners[]` by exact `runner_id == "trail-review"`; current-passed requires `state == "evaluated"`, `outcome == "passed"`, and `evaluated_at_sha == head_sha`, with the Trail head matching the current PR head. Record absent/not-configured, running, stale, failed, and current-passed distinctly; an empty auxiliary summary is never main-review evidence. Genuine absence is not a passing required review; report the configuration/evidence gap. Unavailable detail names the next authenticated observation, not another review run.

Check Trail status before mergeability: `.status == "merged"` may coexist with false `.mergeability.mergeable`; report direct merge confirmation to the parent without restarting review. For open Trails, `.mergeability.mergeable` and `.mergeability.gates[]` are corroborating evidence only; Entire Ready-to-merge never substitutes for Alex's personal current-head gates. When those gates hold, approval-only Entire failure means **automated work complete; human handoff**, not another review run or an automated approval-polling condition.

The GitHub check named exactly `Partial Gates` is always an environment/testing artifact. The owner and steward never inspect, wait on, fix, or report it as required; it does not block merge readiness. This does not apply to `Entire Gates` or any differently named check.

For human-facing owner reports (not artifact creation), verify a Trail match only from an actual link or association; repository or branch similarity is not evidence. When one or more verified matching Trails exist, show only their full clickable canonical Trail URL(s) and Trail state; do not identify or link the matched PR, including its URL, number, or identity. PR-derived evidence such as mergeability, check status, and unresolved-thread counts may remain in prose without identifying or linking the PR. If the Trail association exists but Trail state/detail is unavailable, show the Trail URL as unknown and do not fall back to the PR. A closed, merged, or unknown matching Trail remains primary; report its state or discrepancy rather than switching artifacts. If no matching Trail exists, show the clickable PR URL with `Trail: pending/not linked`. For multiple verified matching Trails, show all their canonical URLs and no PR. Never guess or manually create a Trail. Keep artifact creation, automatic Trail linking, review mechanics, personal gates, post-merge verification, and structured/internal PR evidence unchanged. Pi and Claude bottom status lines remain Trail-only.

Return only aggregate review receipts to the parent: PR/current SHA, **current-head mergeability** (`MERGEABLE`, `UNKNOWN`, or `CONFLICTING`) with its next action/signal, required-check summary (excluding `Partial Gates`), Bugbot status for that SHA, unresolved-thread count, trail/open-finding count, main-review receipt (Trail status/head, runner ID/state/outcome/evaluated SHA, Entire gate summary), **monitor receipt** (PR/Trail head, each monitor's value/state/evaluated SHA, per-canonical-classification disposition counts, evidence-recorded status, actionable count, insufficient-evidence count, and next signal), and merge readiness. Monitor rationale and per-claim evidence stay with the owner and steward. A merge-ready receipt requires `mergeable == "MERGEABLE"` on the current PR head, Bugbot terminal, current-passed main review, green required CI excluding `Partial Gates`, zero unresolved threads, and zero open Trail findings; every monitor present in `.monitors[]` evaluated on the current PR and Trail head; no present monitor evaluating, stale, or failed; absent keys recorded as `not configured` without blocking or `insufficient_evidence`; zero verified actionable and insufficient-evidence claims; and documented `no-action` dispositions for stale or opinion claims. A non-ready receipt must name its next signal or action. The parent may coordinate or nudge with aggregate discrepancies, but it never prescribes review fixes or launches a competing steward.

## Publish local Trail footer state

When the owner/steward or its existing watch already observes the Trail's actual `open`, `draft`, `merged`, or `closed` status, publish it with `node ~/.pi/agent/extensions/session-trail-footer/record-state.mjs "$trail_url" "$trail_status" "$observed_at"`. Inside the actual owning Herdr workspace, the helper automatically records the workspace's own Trail association, even without a parent's hand-written ledger. It does not create any parent edge. A relay from another workspace must append `--workspace <actual-owner-id> --pane <actual-owner-pane-id>` from the verified launch receipt, rather than associating the Trail with the relayer. The third argument is the ISO observation timestamp; omit it only for a fresh direct observation, and preserve it when relaying a receipt. Publish when linking the Trail and when the existing workflow observes a status change, including final closure. This writes only local footer state outside the checkout and is safe while the steward owns repository writes. It does not create/link a Trail or replace the parent's ownership ledger. Never make an extra remote request or launch another watch for the footer, and never infer Trail status from PR readiness, PR merge, approvals, or cleanup. Lookup failure preserves last-known local state. Include the canonical Trail URL, actual status, and observation timestamp in the parent's aggregate receipt so it can relay the same evidence without another fetch.

## Escalate only these cases

- an unsettled product or scope decision;
- a cross-piece contract change;
- a destructive or security-sensitive action not already authorized;
- a blocker for which every safe path would be a guess.

Everything else—including replacing a parent technical hypothesis—is yours to resolve and continue.

## Progress and cleanup receipts

Keep a readable progress record and provide receipts containing:

- decisions and replaced hypotheses;
- implementation and verification results;
- PR and review state;
- residual risks or blockers;
- every resource started (Compose project, server, tunnel, temporary state); and
- exact, idempotent cleanup commands and intentional retained resources.

Before review, stop resources no longer needed. Update the receipt if review work starts a resource. After direct merge confirmation, wait for the parent's current merge-commit success receipt for default-branch builds/checks before the final repository-specific cleanup pass. The parent owns the event-driven post-merge watch; the review steward remains pre-merge. Report post-merge failures to the parent, including apparently unrelated failures with evidence, rather than silently ignoring them or cleaning. Once the parent authorizes cleanup after that receipt, report the cleanup receipt and leave the checkout clean and unoccupied.

Never remove the Herdr workspace yourself. The parent verifies cleanup and removes it only after merge confirmation and post-merge success. No final cleanup or Done receipt before both. If you crash, the parent may run only cleanup commands already recorded, one at a time after inspection.
